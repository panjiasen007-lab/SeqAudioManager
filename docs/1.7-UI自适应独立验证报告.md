## 四、源码缺陷 QA-UI-02：最小窗表格被父容器裁切，实际只剩 3 行（P2）

### 现象（可复现，确定性，不是 flaky）

1040×720（软件自身申报的最小窗口）下：

| 量 | 值 |
|---|---|
| `table.height()`（表格自报） | **360 px** |
| `table.parent().height()`（真正的容器） | **206 px** ← **比表格还矮 154 px** |
| `table.visibleRegion().height()`（Qt 裁切后的真实可见高） | **128 px** |
| 表头高 | 35 px |
| 真实可见视口 | 128 − 35 = **93 px** |
| 行高 | 34 px |
| `rowAt()` 命中的可见行 | **3 行**（第 4 行被切断） |

即：**「最小窗下表格至少显示 10 行」这条承诺不成立，用户实际只看到 3 行**，且表格下半截（含横向滚动条、纵向滚动条下端）被父容器直接裁掉，视觉上是断行。

### 证据

1. 独立用例稳定失败：
   `AssertionError: 360 not less than or equal to 206 : 1040×720：表格自报高 360px 超过父容器 206px，超出部分会被 Qt 裁掉（QA-UI-02 的成因）`
2. 离屏截图 `D:/tmp/grab_720.png`：表头 + 3 行后被一条亮线切断，下方露出被压住的区域。
3. 对照 `D:/tmp/grab_1040.png`（1920×1040）：表格完整不裁切，可见 12 行——说明**只在窗口高度不足时发生**。

### 根因

- `src/seqaudio/ui/main_window.py:152` 把窗口最小尺寸写死成 `setMinimumSize(1040, 720)`；
- 而布局的真实最小高度远大于 720：单是表格区 `_enforce_table_min_height()` 就要 360 px，加上 chips 78 px、底部 170 px、播放条/进度条/工具栏/状态栏 ≈ **850 px 以上**；
- Qt 因此把中间 splitter 压到 **206 px**，而表格带着 `setMinimumHeight(360)` 不肯缩，结果**溢出父容器**——`QLayout` 不会替你裁，Qt 只是按父矩形裁剪绘制，于是只露出最上面 93 px 视口。
- 本条**不是本次改动的回归**：在改动前的 `e29be24` 上同一测法为「父容器 188 px / 可见视口 75 px / **2 行**」。本次改动把它从 2 行提到 3 行（底部 190 固定 → 170 自适应，多让出 18 px），但**离 10 行仍差 7 行**，且新增注释明确宣称"保住表格 10 行下限"，与实际不符。

### 4.3 采纳的修法（产品与工程共同定稿：不裁切优先）

最初我建议「把最小窗口高度抬到 ≈850」，被否决——1366×768 笔记本上窗口会超出屏幕，比裁切更糟。最终采纳：

| 措施 | 说明 |
|---|---|
| 最小窗口保持 1040×720 | 不牺牲小屏可用性 |
| 底部下限 170 → 120 | 小窗时把高度让给表格（实测受三栏 minHint 限制，只能到 **158**，见 4.4） |
| 表格 `minimumHeight` 改为 `min(期望10行高度, 父容器可用高度)` | 新增 `_sync_table_min_height()`，从根上消除「声明高度 > 容器高度 → 溢出被裁」 |
| 验收口径统一用 `visibleRegion()` | `table.height() >= table.minimumHeight()` 是几何恒等式，对裁切问题恒为真（假绿） |

### 4.4 纵向预算实测：为什么小窗守不了 10 行（3/6/10 分档的依据）

**底部三栏各自的 `minimumSizeHint().height()`（决定了底部压不到 120）：**

| 栏 | minHint |
|---|---|
| pane0 运行日志 | 113 |
| **pane1 歌词面板 `PlayerLyricsPanel`** | **140** ← 真正的瓶颈 |
| pane2 信号路径 | 63 |

底部整体 `minimumSizeHint = 140`，实测 `minimumHeight()` 被抬到 **158**，所以 `setFixedHeight(120)` 落不了地。

**1040×720 的纵向预算（实测）：**

```
central 690 = brandBar 56 + body 634
body 634    = 过滤行 74 + 区块头 70 + 表格区 218 + 播放条 56 + 底部 158 (+spacing)
表格区 218  = chips 78 + 表格 140
表格 140    → (140 − 表头 35) ÷ 行高 34 ≈ 3 行
```

- 底部即使真能到 120（多让 38 px）：表格 178 → **4 行**；
- 要到 6 行需表格 239 px，即底部压到 **≈74 px**——比歌词面板的 140 硬底还小 66 px，**物理不可能**；
- **10 行需要表格 35 + 10×34 = 375 px**，按当前 chrome 推算窗口高度要到 **≈1000 px**（实测 1920×1040 已有 12 行）。

**定稿口径（产品与工程确认，QA 按此写用例）：**

| 窗口 | 断言 |
|---|---|
| 1040×720 | **不裁切**（`table.height() <= parent.height()`、`visibleRegion ≈ table.height()`、纵向滚动条完整）+ 可见行 **≥3** |
| 1420×880 | 不裁切 + 可见行 **≥6** |
| 高度 ≥1000（实测 1920×1040） | 不裁切 + 可见行 **≥10**（实测 12） |

> 决策理由：不为了"最小窗 10 行"去改底部三栏结构（标签页/折叠），那会推翻用户明确要求的"左中右三等分"；改为**把"10 行"的承诺挪到高度够的窗口上守**，小窗守"不裁切 + 尽量多"。配套措施：默认启动高度按屏幕自适应（1080p 屏首次打开约 1000 px，即 10~11 行；768p 屏不超屏）。

### 4.5 用例的"红→绿"双状态验证（证明断言不是恒真）

同一份用例在两个状态下跑：

| 状态 | 结果 |
|---|---|
| `abe8fc6` 干净检出（未修） | **2 条红**：`360 not less than or equal to 206`（720）、`360 not less than or equal to 343`（880） |
| 工程师工作区（已加 `_sync_table_min_height`） | **11/11 OK**（7.463 s），720 下 `table.height()=140 <= parent 218`，裁切症状消失 |

## 五、`test_hide_until_eof_auto_advances` flaky 定性

### 5.1 复现尝试（10 次，全过）

| 场景 | 次数 | 结果 | 耗时 |
|---|---|---|---|
| 单跑该用例（空载） | 5 | **5/5 OK** | 5.828 / 5.772 / 5.796 / 5.691 / 5.736 s |
| 单跑该用例（4 核 CPU 满载） | 3 | **3/3 OK** | 5.827 / 5.840 / 5.871 s |
| 全量 discover（`abe8fc6`，589 项） | 1 | **OK** | 411 s |
| 整文件 `test_ui_modes_independent.py`（17 条） | 1 | **17/17 OK**（含本用例） | 220 s |

工程师只报告了 1 次失败（`queue_index 0 != 1`），此后 2 次全量 + 我这边 10 次都没有再现。

### 5.2 时间预算拆解（脚本打时间戳，5 轮）

```
round1: start_latency=0.106s  eof_at=3.383s  index=1 state=PLAYING   PASS
round2: start_latency=0.105s  eof_at=3.373s  index=1 state=PLAYING   PASS
round3: start_latency=0.105s  eof_at=3.374s  index=1 state=PLAYING   PASS
round4: start_latency=0.105s  eof_at=3.380s  index=1 state=PLAYING   PASS
round5: start_latency=0.105s  eof_at=3.388s  index=1 state=PLAYING   PASS
```

- 素材长 **3.2 s**；从 `play_index(0)` 到真正出声 **≈105 ms**；到 `queue_index` 变 1 约 **3.38 s**。
- 用例给的预算：`_enqueue_two()` 里的 `pump(0.4)` + 断言前的 `pump(4.2)` = **4.6 s 墙钟**。
- 余量 = 4.6 − 3.38 ≈ **1.2 s**。也就是说：只要设备开流被占住/音频线程被饿住超过 1.2 s（≈曲长的 37%），断言就会在 `queue_index` 还是 0 时执行。
- 全量 discover 里，本文件排在 `test_player_output` / `test_player_exclusive` 之后，那两个文件**真开流**占用同一个物理输出设备；MME 释放有滞后，正好属于"开流被占住"的场景。

### 5.3 结论与处置（已按结论落地改动）

- **证据不支持"引擎会丢 EOF"**：10 次运行中，只要给够时间，`queue_index` 每次都稳定在 3.38 s 左右变 1；且 `state` 始终 `PLAYING`，没有出现 IDLE/错误。
- **判定为测试侧等待余量不足**：用「固定墙钟 4.2 s」去等「3.2 s 音频 + 变化的开流延迟」，本质是脆断言。
- **已改测试（不动源码）**：`test_hide_until_eof_auto_advances` 改成**每 50 ms 轮询 `queue_index`、上限 `EOF_TIMEOUT_SEC = 12.0`**，循环体内断言 `state` 不得退化，失败信息带上"已过多少秒"。提交 `20592b2`。
- **改后 10 次实跑全过**：4.662 / 4.687 / 4.610 / 4.576 / 4.564 / 4.693 / 4.694 / 4.694 / 4.808 / 4.559 s。因为改成"条件成立即返回"，该用例从 5.7 s 降到 **4.6 s**。
- 若今后仍在 12 s 内偶发 `index 0`，那就不是余量问题，应转工程师查引擎 EOF 判定。

| `test_player_engine.TestEnginePlayback.test_signal_path_reflects_fallback` | `engine.play()` 返回 `False`（开流失败） | **OK（0.500 s）** |

**定性**：本机只有一块物理输出设备。`test_player_output` / `test_player_exclusive` 里真开流的用例 `stop()` 之后，PortAudio / 驱动释放设备有几十~几百毫秒滞后；全量串行时紧随其后的真开流用例就吃到 `-9996`。单跑时设备空闲，复现不了。与这批 UI 改动无关（`ad3a2c4` 只动 `main_window.py`）。

**稳定化实现**（`tests/device_retry.py`，新增）：

| 约束 | 实现 |
|---|---|
| 只重试设备忙 | 仅 `err == -9996` 或文本含 `Invalid device`；其它错误码（`-9997`/`-9985`/…）**一次都不重试**，直接失败 |
| 有界 | 最多 **2 次**重试（共 3 次尝试），每次退避 **200 ms** |
| 不静默 | 每次重试写 `WARNING` 日志，含「第 N 次重试」与动作名 |
| 覆盖 bool 型 API | `PlayerEngine.play()` 只回 `False`：从 `snapshot()["error"]` 读到 `-9996` 时抛 `DeviceBusyHint`，交给同一套重试 |

**注入式验证（证明重试链路真的生效，不是写了没用）**：

```
[WASAPI 独占用例] 伪造前 2 次 prepare 抛 -9996 →
  prepare 调用次数: 3（1 次 + 2 次重试），用例通过
  WARNING … WASAPI 独占 44.1k 开流：开流失败（… -9996），第 1 次重试（200 ms 后）
  WARNING … 第 2 次重试（200 ms 后）

[引擎回退用例] 伪造前 2 次 play() 返回 False 且 error 含 -9996 →
  play 调用次数: 3，用例通过，同样两条重试日志
```

**边界自测**（`tests/test_device_retry.py`，6 条）：重试后成功 = 3 次尝试 / 退避 2 次；一直失败 = 3 次后抛出（不无限重试）；`-9997`/`-9985`/`-9999` **0 次重试**；每次重试都有 WARNING 且含「第 N 次重试」。

> 该 flake 与 §五 的 EOF flaky **同源**：同一台机器只有一个输出设备，多个"真开流"用例互相干扰。§五 用"轮询到条件成立"解决，本节用"有界重试"解决，两者都没有用"全局 sleep 加长等待"来糊。
